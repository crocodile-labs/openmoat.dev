Every allow, and what it opens

Each way to let the agent do more, side by side: what it covers, how long it lasts, what stays protected and what to think about.

Read this when you are about to allow something and want to know exactly what changes.

Two facts hold for every allow below:

  • Deny rules always win. No allow opens your keys, .env files, cloud credentials, destructive commands or OpenMoat's own files.
  • Allowed means no prompt at all. OpenMoat tells the agent the call is allowed, so the agent does not ask you either.

Every rule moat allow adds is in ~/.moat/policy.d/approved.yaml, with its id and the date.

#moat allow --last

What this opens

  • The one call OpenMoat just asked about, in that agent session

What stays protected

  • A new session asks again; other commands and files are not covered

Think about

  • Low risk: you saw the exact call

#moat allow --last --always and moat allow "<command>" --always

What this opens

  • A command rule matches the command and the same command with more arguments: npm run build also allows npm run build -- --anything
  • A file rule matches exactly the files of that ask, nothing below them

What stays protected

  • Hosts the command connects to are not covered: curl https://example.com is still denied for that host
  • Deny rules on what the command reads or writes still win

Think about

  • Allow the shortest command that is safe with anything after it. Never allow a bare interpreter (python, node, bash)

#moat allow --dir <folder>

What this opens

  • Every file in the folder and below: read, create, edit and delete
  • Programs the agent runs can use it too: the sandboxes are updated at once

What stays protected

  • .env files, keys and agent settings in it stay denied
  • Writes into .git there, CI workflows and commit-hook files are left out of it
  • Home, a folder above it and / are refused

Think about

  • The agent can edit build files there (package.json scripts, a Makefile) that you run later. Allow folders you work in, not a parent of repositories you have not checked

#moat allow --site <host>

What this opens

  • Web fetch tools reach the host without a prompt
  • Shell commands to it go to your agent's prompt instead of being denied

What stays protected

  • Every other host, subdomains included, stays denied

Think about

  • The host can receive whatever the agent sends it. Never allow paste sites, webhook catchers or file-sharing hosts

#moat secret add <id>

What this opens

  • Programs the agent runs can use the token, for that one host

What stays protected

  • The agent holds a placeholder, never the value
  • Its source is denied too: the command adds secret-<id> when no rule covers it (Keep a token from the agent)

Think about

  • Give the token the smallest scope that works

#moat trust

What this opens

  • The repository's allow rules apply, for you, in that checkout

What stays protected

  • Your deny rules still win; the repository's deny and ask rules always apply, trusted or not
  • Any change to the file (a pull, a branch switch) drops its allow rules until you trust it again

Think about

  • Read the rules it prints before you trust: they can widen your asks and defaults

#What allows can never open

  • Reading or writing ~/.ssh, ~/.aws, ~/.gnupg, ~/.kube, ~/.config/gh, ~/.config/gcloud, ~/.azure, ~/.docker/config.json, ~/.netrc, ~/.npmrc, ~/.pypirc, cargo credentials, shell history, keychains, .env files.
  • Printing secret environment variables or the whole environment.
  • curl … | sh and decoded payloads piped to a shell.
  • Force pushes, hard resets, deleting your home folder.
  • Editing your shell startup files.
  • Changing, approving for itself or uninstalling OpenMoat.

To change one of those you edit the deny rules themselves with moat edit, and OpenMoat shows you the diff first.
