<Aside type="note" title="Read this when">

You want to know how much OpenMoat can do for the agent you use, or `openmoat status` shows a protection level you did not expect.

</Aside>

Each agent calls `openmoat guard` from its own **hook** before every tool call. `openmoat init` finds the agents installed on your machine and asks before setting up each one.

For an agent with an **OS sandbox**, `openmoat init` also writes the sandbox settings from the same policy, so a script inside an allowed `npm test` cannot read your keys either. For the others, the hook is the only check; there, running a script the same session wrote needs review first ([Code the agent wrote](/docs/session-written-code/)).

## At a glance

OpenMoat checks {agentCount} agents: {agentList()}.

<AgentTable variant="glance" />

`openmoat status` prints the level each agent has right now. It says **not protected** when the hook is missing or out of date, when the agent's own settings turn hooks off, when OpenMoat's entry lacks the agent's fail-closed key (`failClosed: true` for Cursor, `fail_closed: true` for Hermes Agent), when Hermes Agent's `shell-hooks-allowlist.json` does not approve the hook, when the agent ran without loading OpenMoat's plugin, or when the agent's version does not load OpenMoat's hook (OpenCode before 1.3.4); the line names the file and the setting. When the agent's installed version has a published security advisory that a later version fixes, `openmoat status` and `openmoat doctor` add a warning line naming the version to upgrade to.

For any agent, `openmoat run -- <agent>` starts the whole agent inside one sandbox made from your policy, with network only through OpenMoat's proxy (macOS 13 or later, Linux). It answers nothing command by command; that is the hook's job. See [Auto-approve and CI](/docs/auto-approve-and-ci/#run-a-whole-agent-in-a-sandbox).

Each week CI installs every agent's latest release and sets it up with `openmoat init`; where the agent runs without an account, CI checks that the real agent loads OpenMoat's hook ([what is checked per agent](https://github.com/crocodile-labs/openmoat/blob/main/scripts/ci/latest-agents/README.md)).

## What each agent's hook sees

Every hooked agent sends OpenMoat its shell commands, file reads and writes, and MCP tool calls. A tool OpenMoat has no mapping for is still checked for the paths, URLs and shell commands its arguments name, so an extension's tool that reads `~/.ssh/id_rsa` is denied. The differences are below.

### Claude Code

- **Checked:** `Bash`, `Monitor`, `PowerShell` (not parsed, so it goes to your agent's prompt), file tools (`Read`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `Glob`, `Grep`, `LSP`), `WebFetch`, `WebSearch`, `SendFile`, the local files `Artifact` and `ArtifactData` upload or save, and MCP tools. A second hook, `ConfigChange`, sees settings files change during a session. A third, `SessionStart` (from 0.12.0), gives each session's sandboxed commands their own credential for `openmoat proxy`, so the proxy records their requests under the session and applies its taint ([Agent sessions only](/docs/egress-proxy/sessions/)).
- **Sandbox:** Claude Code's sandbox covers `Bash`, `PowerShell` and `Monitor`. File tools, `WebFetch` and MCP servers run outside it and are checked by the hook only. On native Windows `openmoat init` leaves the sandbox off, because Claude Code would not start with it; run Claude Code and `openmoat` inside WSL2 for it. Where the sandbox is not in place, running a script the session wrote needs review.
- **If the hook fails:** with Claude Code 2.1.295 or later, `openmoat init` sets `onFailure: "block"`, so the call is blocked when `openmoat` cannot start, crashes or times out. Earlier versions run the call unchecked.
- **Turned off by:** `disableAllHooks` in a `settings.json`. A project's `.claude/settings.json` is loaded when the session starts, before any hook runs; see [Project settings that turn hooks off](/docs/blocked/#project-settings-that-turn-hooks-off).

### Codex

- **Checked:** shell commands, `apply_patch` (every file the patch names) and MCP tools. Codex's web search and hosted tools are not sent to hooks, so OpenMoat does not see them.
- **Reviews:** Codex hooks cannot show a question, so a review is sent as a deny. The message says to run `openmoat` or `openmoat allow --last`; run it, then ask Codex to retry.
- **One step in Codex:** Codex runs a new or changed hook only after you trust it in its `/hooks` view. After `openmoat init`, and after an upgrade that rewrites the hook, open `/hooks` in Codex and trust OpenMoat's. `openmoat init` and `openmoat doctor` remind you.
- **If the hook fails:** Codex runs the call unchecked when `openmoat` is missing, crashes or times out.
- **Turned off by:** `[features] hooks = false` in `config.toml`.

### Cursor

- **Checked:** shell commands, MCP calls, file reads, and the agent's file, search and web tools. The hooks are installed with `failClosed`, so a hook that fails blocks the call; an entry without `failClosed: true` is reported as not protected.
- **Reviews:** Cursor shows its own prompt only for shell and MCP calls. A review of a file tool is sent as a deny that says to run `openmoat allow --last`.
- **Sandbox:** `openmoat init` writes Cursor's `sandbox.json` on macOS and Linux. Cursor still runs some commands outside it: one its Auto-review approves, everything in Run Everything mode, and the Cursor CLI without `--sandbox enabled`. Inside the workspace its sandbox cannot deny `.env` or `.git`. Cursor documents no sandbox on Windows, so there it is hook only, and running a script the session wrote needs review.

### OpenClaw

- **Checked:** every tool, through OpenMoat's plugin on OpenClaw's `before_tool_call` hook: `exec`, file tools, `apply_patch`, `web_fetch`, `web_search`, browser navigation and uploads, MCP tools, plugin changes, and cron jobs (which need review).
- **The call that runs is the one checked.** The plugin decides at the highest priority and returns the parameters it checked at the lowest, so another plugin's rewrite of the call is undone ([OpenClaw runs the call OpenMoat checked](/docs/agents/openclaw/)). A plugin that changes the call and asks for approval in the same answer keeps its change once you approve it.
- **Setup:** restart the Gateway after `openmoat init` (`openclaw gateway restart`). `openmoat init` refuses an `openclaw.json` that has comments, because writing it back would drop them: move them out first.
- **If the hook fails:** a plugin that throws or takes over 60 seconds blocks the call. If the Gateway does not load the plugin at all, calls run unchecked; `openmoat status` says "plugin not loaded yet" until the plugin has reported loading ([Plugin loading](/docs/agents/plugin-loading/)).
- **Not checked:** OpenClaw's process input to a running `exec` session; `code_execution`, which runs at the model provider. Running a script the session wrote needs review.

### GitHub Copilot CLI

- **Checked:** every tool, through a `preToolUse` hook in a file of OpenMoat's own (`~/.copilot/hooks/openmoat.json`): `bash`, file tools, patches, searches, `web_fetch`, `web_search` and MCP tools. Input typed into a running shell (`write_bash`, `write_powershell`) needs review, because a command split over two calls would pass piece by piece.
- **Reviews:** Copilot's own prompt. In autopilot mode Copilot turns a review into a deny.
- **If the hook fails:** Copilot blocks a call whose hook crashes, but runs one whose hook times out. `openmoat init` sets the timeout to 600 seconds, far above OpenMoat's own 30-second limit.
- **Turned off by:** `disableAllHooks` in `~/.copilot/settings.json` or a repository's `.github/copilot/settings.json`. The agent cannot write those files, and `openmoat status` reports yours.

### pi

The pi coding agent (`@earendil-works/pi-coding-agent`).

- **Checked:** every tool, through OpenMoat's extension (`~/.pi/agent/extensions/openmoat.js`) on pi's `tool_call` event, including the calls a `codemode` script makes and the tools of other extensions.
- **Reviews:** a pi dialog. In print and JSON mode, which have no screen, a review is a deny until you run `openmoat allow --last`.
- **Deferred calls run.** pi has no approval step of its own, so a call OpenMoat has no rule for runs without a question.
- **Setup:** restart pi after `openmoat init`; it loads extensions when it starts.
- **If the hook fails:** an extension that throws, or an answer that takes over 45 seconds, blocks the call. `pi --no-extensions`, or a settings entry that leaves OpenMoat's extension out, runs calls unchecked; `openmoat status` reports such an entry, and reports pi as not protected once pi wrote a session without the extension reporting that it loaded ([Plugin loading](/docs/agents/plugin-loading/)).
- **Not checked:** an input change by an extension pi loads after OpenMoat's, and an extension that replaces a built-in tool.

### Gemini CLI

- **Checked:** every tool, through a `BeforeTool` hook in `~/.gemini/settings.json`: `run_shell_command`, file tools, searches, `web_fetch`, `google_web_search` and MCP tools. A search without a directory, and every `read_many_files`, needs review, because Gemini CLI then reads every workspace folder and the hook does not say which.
- **Reviews:** Gemini CLI's own confirmation, also in YOLO mode.
- **Trusted folders only.** In a folder Gemini CLI does not trust, it runs no hooks at all, and asks you before every tool instead.
- **If the hook fails:** Gemini CLI has no setting to block on failure. A hook that times out, is killed or exits with code 1 lets the call run. A missing `openmoat` blocks it.
- **Setup:** `openmoat init` refuses a `settings.json` with comments: move them out first. When Gemini CLI saves a new model, theme or display setting there, calls keep being checked and `openmoat doctor` reports the change.

### OpenCode

OpenCode 1 (`opencode-ai`, 1.3.4 and later) and OpenCode 2 (`@opencode/cli`), through one plugin ([OpenCode 1 and 2](/docs/agents/opencode/)).

- **Checked:** every tool, through OpenMoat's plugin (`~/.config/opencode/plugins/openmoat.js`) on OpenCode 1's `tool.execute.before` or OpenCode 2's `execute.before`. The plugin pins the call it checked, so a later plugin that rewrites it makes the call fail.
- **Reviews:** on OpenCode 2, OpenCode's own permission prompt. OpenCode 1 gives a plugin no way to prompt you, so a review is a deny that says to run `openmoat` or `openmoat allow --last`. A call OpenMoat defers is left to OpenCode's own permission rules.
- **Setup:** start OpenCode again after `openmoat init` (OpenCode 2: `opencode service restart`). An upgrade from 1 to 2 needs no new `openmoat init`. OpenCode before 1.3.4 is not set up: `openmoat status` says to upgrade.
- **If the hook fails:** a plugin that throws, or an answer that takes over 45 seconds, blocks the call. OpenCode runs calls unchecked when it does not load the plugin: OpenCode 1's `--pure` or `OPENCODE_PURE`, OpenCode 2's `-openmoat` in `plugins`, or an error loading it. `openmoat status` says "plugin not loaded yet" until the plugin has reported loading.
- **Not checked:** your own `!` shell commands. OpenCode 2's `--auto` approves OpenMoat's reviews, and the plugin cannot tell. Other plugins and custom tools run in OpenCode's process with the agent's rights, and a project's load at start with no prompt.

### Hermes Agent

- **Checked:** every tool, through one `pre_tool_call` shell hook in `~/.hermes/config.yaml` (`$HERMES_HOME/config.yaml` when that is set), with `fail_closed: true`. `openmoat init` edits the file as text, so your comments stay, and approves the hook's command in `shell-hooks-allowlist.json` beside it. Its `memory` and `skill_manage` tools are checked as writes of its `memories/` and `skills/`.
- **Reviews:** Hermes's own approval prompt. In YOLO mode or with `approvals.mode: off`, where Hermes would approve it unseen, a review is a deny you approve with `openmoat allow --last`.
- **Setup:** restart `hermes` and the gateway after `openmoat init` (a running gateway picks the hook up within about 30 seconds). Hermes saves `hermes model` and display choices in the same file without affecting OpenMoat; any other change there denies every call until you run `openmoat doctor --accept`.
- **If the hook fails:** a hook that cannot start, times out, exits non-zero without a decision or prints something that is not JSON blocks the call, and so does `plugins.hook_callback_timeout` (30 seconds by default) running out. Hermes runs a call unchecked when its own hook dispatcher raises an error.
- **Skipped hook:** Hermes's gateway, cron and ACP sessions skip a hook its `shell-hooks-allowlist.json` does not approve, as Hermes does under `HERMES_SAFE_MODE=1` or in a profile OpenMoat did not set up. `openmoat status` reports a hook the allowlist does not approve as not protected.
- **Not checked:** what an `execute_code` script does itself (its tool calls are checked). Plugins, another hook's `modify` reply and tool middleware can rewrite a call's arguments after the check. The in-session `/yolo` toggle and `hermes -z` approve a review unseen. Terminal commands on a remote backend (docker, ssh, modal, …) are checked as local ones.

### Cline CLI

The Cline CLI (`cline`, npm `@cline/cli`). Setup, the tools it checks and the limits in full: [Cline CLI](/docs/agents/cline/).

- **Checked:** every tool, through OpenMoat's `PreToolUse` hook script in `~/.cline/hooks` (`$CLINE_DIR/hooks` when that is set): `run_commands`, `read_files`, `editor`, `apply_patch`, `search_codebase`, `fetch_web_content` and MCP tools; any other tool by the paths, URLs and commands its arguments name. The MCP servers in Cline's `cline_mcp_settings.json` are pinned.
- **Reviews:** Cline's hooks cannot prompt, so a review is a deny, which ends Cline's run. Approve it with `openmoat allow --last` and continue the session.
- **If the hook fails:** Cline itself runs a call whose hook fails, so OpenMoat's script blocks the call when `openmoat` is missing, crashes or gives no answer. A script that cannot start at all (no `sh`) or is killed after Cline's 120 seconds lets the call run.
- **Not checked:** the Cline VS Code extension, `--yolo` runs (no hooks run at all) and native Windows.

### goose

goose, the open-source agent from Block, CLI and desktop app. Setup, the tools it checks and the limits in full: [goose](/docs/agents/goose/).

- **Checked:** every tool, through OpenMoat's plugin, `~/.agents/plugins/openmoat/hooks/hooks.json`, one `PreToolUse` entry with `on_failure: block`: `shell`, `write`, `edit`, `tree`, `analyze`, `read_image` and extension tools. MCP extensions in goose's `config.yaml` are pinned.
- **Reviews:** goose hooks cannot prompt, so a review is a block you approve with `openmoat allow --last`.
- **Setup:** restart goose (the CLI or the desktop app) after `openmoat init`; it loads plugins when it starts.
- **If the hook fails:** with `on_failure: block`, which `openmoat init` sets, a hook that cannot start, times out or answers wrongly blocks the call. goose runs every call unchecked when it does not load the plugin.
- **Not checked:** what Code Mode's `execute_javascript` does (its tool calls skip the hook, so the call itself needs review), and hooks a project's `.agents/plugins/` adds.

### Continue CLI

The Continue CLI (`cn`) is built to run Claude Code's hook, but the released `cn` runs no hooks yet, so OpenMoat cannot check its calls. Start it with `openmoat run -- cn` to keep it in a sandbox; `openmoat doctor` warns about this.

## macOS, Linux and Windows

| | Hooks | Agents' own sandboxes | `openmoat run` | `openmoat proxy install` |
|---|---|---|---|---|
| macOS | yes | Claude Code, Codex, Cursor | macOS 13 or later | launchd user agent |
| Linux | yes | Claude Code, Codex, Cursor | yes, plus `--isolate` | systemd user unit |
| Windows | yes (not the Cline CLI) | Codex only; use WSL2 for Claude Code | no; use WSL2 | not yet |

- **macOS:** `openmoat run` uses Seatbelt and needs macOS 13 or later. On macOS 12 it refuses to start and says so; the hooks still apply the policy.
- **Linux:** `openmoat run` uses Landlock and seccomp. Where bubblewrap can run, the agent also gets a network namespace of its own, so its traffic can only go through OpenMoat's proxy. Without it the network is limited by port only, and `openmoat run` says so on every start (`--netns=require` refuses to start instead). Plain `openmoat run` does not protect files inside the project (`.env`, `.git`, `.moat`); `openmoat run --isolate` does.
- **Windows:** the hooks apply the policy to every call, except for the Cline CLI, which is not covered on native Windows (its hook script needs `sh`). goose on Windows needs `sh` on the search path to run any hook; without it every call is blocked. PowerShell commands are not parsed, so OpenMoat never allows one: they go to your agent's prompt. Secrets kept in the system keychain cannot be brokered yet.

## Agent settings that switch the hook off

An agent's own settings can turn its hooks off, and OpenMoat cannot override them. `openmoat status` and `openmoat doctor` report the ones in your own settings as **not protected**, and warn about a project's settings that turn hooks off, add hooks or start programs:

| Agent | Setting |
|---|---|
| Claude Code | `disableAllHooks` in `settings.json` |
| Codex | `[features] hooks = false` in `config.toml`, or OpenMoat's hook not trusted in `/hooks` |
| GitHub Copilot CLI | `disableAllHooks` in `settings.json` |
| pi | an `extensions` entry that leaves OpenMoat's out, or `--no-extensions` |
| Gemini CLI | `hooksConfig` in `settings.json`, or a folder Gemini CLI does not trust |
| OpenCode | `-openmoat` (or `-*`) in `plugins`, or a `policies` entry denying OpenMoat's plugin, in `opencode.json[c]`; OpenCode 1's `--pure` or `OPENCODE_PURE` |
| Hermes Agent | the hook's command not approved in `shell-hooks-allowlist.json`; `HERMES_SAFE_MODE=1`; a profile OpenMoat did not set up |
| Cline CLI | `--yolo`; `--config`, `--hooks-dir` or a moved `CLINE_DIR` that OpenMoat did not install into |
| goose | `disabledPlugins` naming `openmoat` in `~/.config/goose/settings.json` or a project's `.config/goose/` |

The agent itself is denied writing your own settings files of these, so only you, or a program running outside the agent, can change them.

Every gap per agent, with the reasons: [THREAT_MODEL.md](https://github.com/crocodile-labs/openmoat/blob/main/docs/THREAT_MODEL.md#5-known-limitations). Every tool each hook sees: [INSTALL.md](https://github.com/crocodile-labs/openmoat/blob/main/docs/INSTALL.md#set-up-with-openmoat-init).
