<Aside type="note" title="Read this when">

The one-command allows are not enough, for example a pattern, a read-only folder or a rule of your own.

</Aside>

Your policy is `~/.moat/policy.yaml`. Most changes need no editing at all:

| You want | Run |
|---|---|
| Read and write a folder | `openmoat allow --dir <folder>` |
| Reach a host | `openmoat allow --site <host>` |
| Allow the command you were just asked about | `openmoat allow --last --always` |
| Take one of those back | `openmoat allow --remove <id>` |

## Edit the policy

```bash
openmoat edit
```

It opens the policy in `$VISUAL` or `$EDITOR`. When you close the editor it checks the policy, shows the diff and asks `Apply? [y/N]`. A policy with errors is never written, and the previous version is kept in `~/.moat/policy.yaml.bak`.

What you see at each step:

| After you close the editor | `openmoat edit` prints |
|---|---|
| Nothing changed | `no changes; the policy was not touched` |
| The policy does not lint | `the edited policy does not lint:` and the error, then `Edit again? [y/N]`; anything but `y` leaves it as it was: `the policy was not changed` |
| It lints | a `warning:` line for each rule that can never match, the diff, then `Apply? [y/N]` |
| You answer `y` | `✔ /Users/you/.moat/policy.yaml updated`, `✔ lock re-pinned (N files)` and the undo line |

Then run `openmoat sandbox sync`, so the agents' OS sandboxes follow the new rules, and start a new agent session.

### Undo an edit

```text
  undo: the previous policy is in /Users/you/.moat/policy.yaml.bak; copy it back and run `openmoat doctor --accept`
```

In your own terminal:

```bash
cp ~/.moat/policy.yaml.bak ~/.moat/policy.yaml
openmoat doctor --accept     # re-pins the restored policy; until then every call is denied (kernel-integrity)
openmoat sandbox sync
```

An `openmoat policy upgrade` is undone with `openmoat policy upgrade --undo` ([below](#new-default-rules-after-an-upgrade)). A rule added by `openmoat allow` comes out with `openmoat allow --remove <id>`; `openmoat allowed` lists them with their ids.

### Test a rule before you apply it

Write the rule into a copy, then decide a command against it:

```bash
cp ~/.moat/policy.yaml ./policy.yaml     # then add the rule to ./policy.yaml
openmoat policy lint ./policy.yaml
openmoat policy check "npm run deploy:prod" --policy ./policy.yaml
```

With `--policy`, only that file decides: the `openmoat allow` rules, packs and a repository's policy are left out. When the verdicts are what you want, make the same change with `openmoat edit`.

### Example: read-only access to every repo under a folder

```yaml
allow:
  - id: work-repos-read
    reason: reference code the agent may read
    fs.read: ["~/work/acme/**"]
```

### Example: always ask before deploying

```yaml
ask:
  - id: deploys
    reason: deploys reach production
    shell: ["npm run deploy*", "fly deploy*"]
```

Rules are tried in the order **deny → allow → ask**, and across one command the strictest answer wins. A deny cannot be overridden by an allow.

## Edit by hand

```bash
$EDITOR ~/.moat/policy.yaml
openmoat policy lint      # schema, ids, globs; warnings for rules that can never match
openmoat                  # shows what changed and asks you to accept it
```

<Aside type="caution" title="Until you accept, every call is denied">

OpenMoat pins the policy. A change no person accepted looks like tampering, so every call is denied with `kernel-integrity` until you run `openmoat` (or `openmoat doctor --accept`). `openmoat edit` and `openmoat allow` re-pin for you.

</Aside>

## New default rules after an upgrade

`openmoat init` keeps your policy, so a rule a new release's default gained is offered, not forced. `openmoat`, `openmoat init` and `openmoat doctor` say "policy update available: N changes".

```bash
openmoat policy upgrade --dry-run   # what the new default adds, as a diff; changes nothing, needs no terminal
openmoat policy upgrade             # shows the diff, asks, keeps a backup and re-pins
openmoat policy upgrade --undo      # put the previous policy back, byte for byte
```

`--dry-run` starts with `Policy update available: N changes from the OpenMoat <version> default`, or says `The policy has every change of the OpenMoat <version> default.` Lines you changed are never touched: a change that would overlap them is listed under `Not applied: you changed the policy at line N; the default now has:`, for you to make with `openmoat edit` if you want it. After applying, it prints `✔ … upgraded (N changes)`, `✔ lock re-pinned (N files)` and a reminder to run `openmoat sandbox sync`. Run it after each upgrade of the binary ([Upgrade](/docs/upgrade/)).

The syntax of a rule: [The policy file](/docs/policy-file/). The full policy language and the default policy are in [POLICY.md](https://github.com/crocodile-labs/openmoat/blob/main/docs/POLICY.md).
