<Aside type="note" title="Read this when">

A new OpenMoat release is out, or `openmoat` says "policy update available". Coming from 0.7 or earlier, when the command was `moat`? Read [Upgrading from 0.7 or earlier](#upgrading-from-07-or-earlier) first. What a release changes, and what it needs you to run: [Releases](/docs/releases/).

</Aside>

<Steps>

1. **Upgrade the binary**

   <Tabs>
   <TabItem label="Homebrew">

   ```bash
   brew update && brew upgrade openmoat
   ```

   The formula is `crocodile-labs/tap/openmoat`. An existing `moat` install moves to it with `brew upgrade`: the tap renames `moat` to `openmoat`.

   </TabItem>
   <TabItem label="Installer">

   Run the installer again (`openmoat-installer.sh`, or `openmoat-installer.ps1` on Windows), as in the [Quick start](/docs/quickstart/). Its URL always fetches the latest release.

   </TabItem>
   <TabItem label="Cargo">

   ```bash
   cargo install openmoat --locked --force
   ```

   It installs both `openmoat` and `moat`.

   </TabItem>
   </Tabs>

   Hooks keep working after an upgrade in the same place. `openmoat doctor` confirms it, and names anything left to do.

2. **Read the release's Upgrading box**

   Each page under [Releases](/docs/releases/) starts with what that release needs, such as `openmoat init` once and then `openmoat policy upgrade` (0.12.0) or nothing at all (0.10.1). Skipped releases? Read the box of each one in between.

3. **Take the new default rules, if you want them**

   Your policy is kept as it is, so a rule the new default gained is offered, not forced. `openmoat` says "policy update available: N changes" and offers to show them.

   ```bash
   openmoat policy upgrade --dry-run   # what the new default adds, grouped; changes nothing
   openmoat policy upgrade --diff      # the same, then the full diff of the policy
   openmoat policy upgrade             # shows the changes, asks, keeps a backup, re-pins and syncs the sandboxes
   openmoat policy upgrade --undo      # put the previous policy back
   ```

   From 0.16.0 it groups what the new default changes (new protections, fewer interruptions, renames, comment updates counted); answer `d` at `[y/N/d]` for the full diff. Lines you changed are never touched. What each line of the output means: [New default rules after an upgrade](/docs/change-the-rules/#new-default-rules-after-an-upgrade).

4. **Check the installation**

   ```bash
   openmoat --version    # prints (OpenMoat) after the version number
   openmoat status       # each agent: hook + OS sandbox, hook only, or not protected
   openmoat doctor       # drift, out-of-date hooks and sandboxes, and what to run for each
   ```

   A hook written by an older release shows as ``hook entry for … is out of date (written by an older OpenMoat); run `openmoat init` ``: run `openmoat init`. Re-run `openmoat init` only when `openmoat doctor` or the release's Upgrading box asks for it; it keeps your policy.

5. **Bring the sandboxes up to date**

   ```bash
   openmoat sandbox sync
   ```

   It rewrites the agents' sandbox settings from the current policy and re-pins them. From 0.16.0 `openmoat policy upgrade` does this itself after you answer yes; run it when you changed the policy another way, or when `openmoat status` shows ``differs from the policy; run `openmoat sandbox sync` ``.

6. **Restart your agents**

   An agent keeps the hook and sandbox it read when its session started. Start a new session; restart OpenClaw's Gateway, pi, OpenCode (OpenCode 2: `opencode service restart`) Hermes Agent with its gateway, and goose. OpenClaw, pi and OpenCode report that they loaded OpenMoat's plugin only from a start after the upgrade: `openmoat status` says "plugin not loaded yet" until then. After `openmoat init` rewrote Codex's hook entry, trust it again in Codex's `/hooks`.

</Steps>

## Keep one OpenMoat installed

An older binary left elsewhere (a Homebrew install beside a `cargo install`) can still be the one a hook runs, and an older binary denies every call over a lock a newer release wrote. `openmoat doctor` names it: `hook runs …, which does not exist`, `hook runs …, a different OpenMoat binary than this one`, or `lock expects …, running …`. Then:

1. Remove one install.
2. Run `openmoat init` with the one you keep (by its full path, if needed).
3. Run `openmoat proxy install` again if the proxy runs as a service.
4. Restart the agents.

On macOS 12 and earlier, Homebrew may stop and ask for a newer Xcode: upgrade with the installer or `cargo install` instead, then `brew uninstall openmoat` and run `openmoat init` once.

## Upgrading from 0.7 or earlier

From 0.8.0 the command is `openmoat`. Every install still puts a `moat` beside it that runs `openmoat`, for a few releases; then the `moat` name will be removed.

1. Run `brew update && brew upgrade` (or your install method above). The tap renames `moat` to `openmoat`.
2. Run `openmoat init` once, in your own terminal. It backs up each agent's settings file, rewrites OpenMoat's hooks to run `openmoat` instead of `moat`, and re-pins. Your policy is kept.

Until you do, the old hooks keep working through `moat`. `openmoat doctor` says when a hook still uses the old name. OpenMoat's state stays where it was: `~/.moat`, a project's `.moat/policy.yaml` and the `MOAT_*` variables are unchanged, and messages still start with `moat:`.

## What each release needs

**To [0.29.0](/docs/releases/v0-29-0/), from 0.28.0:**

- **Update every `openmoat` on the machine together.** The audit log moves to schema version 13 (a `phases_us` column, which holds each call's time per guard phase); the new build adds it the first time it opens the log, with nothing to run. An older `openmoat` then refuses the log ("audit database schema version 13 is newer than this build supports") and its hook denies every call, so a Homebrew install beside a `cargo install`, say, must move together ([Keep one OpenMoat installed](#keep-one-openmoat-installed)).
- **Restart what keeps running:** a running `openmoat proxy`, `openmoat approvals listen` and any agent with a wrapped MCP server, so that no process of the older build is left. Then run `openmoat doctor` in your own terminal: it names a hook that still runs another binary.
- **The default policy is unchanged**, so `openmoat policy upgrade` has nothing new to offer.
- **New, nothing to turn on:** decisions are faster with the same answers, and `openmoat audit stats` shows the time per guard phase for calls recorded after the upgrade ([Where the guard's time goes](/docs/see-what-happened/guard-time/)).

**To [0.28.0](/docs/releases/v0-28-0/), from 0.27.0:**

- **`openmoat policy upgrade`** offers the new default rules: `encoded-secret-egress` holds a token or credential sent hidden by an encoding (URL encoding, base64, hex, zero-width characters), `hostname-data` holds encoded data in the name of a host no allow rule lists ([Secrets hidden by an encoding](/docs/keep-tokens-safe/encoded-secrets/)), the `data-flow` review holds an MCP tool that acts after another MCP server's result ([Data labels by source](/docs/session-taint/data-labels/), preview), and `kernel-self` also keeps agents away from `openmoat mcp login` and its token folder. From the 0.27.0 default it only narrows. To see what a URL gets: `openmoat policy check --kind fetch '<url>'`.
- **On Windows, `openmoat run` can hold reads and the network too** (preview): run `openmoat agent-account setup` once from an administrator terminal, and later runs start the agent as its own local account; Windows then refuses the reads your policy denies and every connection but the one to the run's proxy. Without it, Windows runs are as in 0.27.0 ([openmoat run on Windows](/docs/sandboxes/windows/#run-the-agent-as-its-own-account-preview)).
- **`openmoat policy check-diff` reads lockfiles**, with no step: a look-alike name, an install script the lockfile records or a `go.sum` hash changed for the same version is flagged in a pull request even when a dependency pulls it in ([Lockfiles in a pull request](/docs/check-a-pull-request/lockfiles/)).
- **New, all optional:** remote (Streamable HTTP) MCP servers through the gateway with `openmoat mcp login <server> --url <url>`, the agent never holding the token ([Remote MCP servers](/docs/mcp-servers/remote-servers/), preview).

**To [0.27.0](/docs/releases/v0-27-0/), from 0.26.0:**

- **`openmoat policy upgrade`** offers `obfuscated` (a line written to hide what it runs is held for review), `Set-ExecutionPolicy` in `persistence`, and more in `kernel-self` (agents kept away from `openmoat team` and the gate's files). From the 0.26.0 default it only narrows ([Hidden commands and PowerShell](/docs/shell-commands/obfuscation-and-powershell/)).
- **`openmoat init` once.** It asks, per hook-only agent, whether typing its name should start it confined; the default is no. `openmoat confine` and `openmoat confine --off` change it later ([Confine agents by default](/docs/sandboxes/confine/)).
- **New denies with no step:** PowerShell lines are read, so a PowerShell listing of `~/.ssh` is denied where it used to be left to the agent; a call OpenMoat cannot decide within its deadline is denied rather than run after the hook times out ([A slow check is denied](/docs/hook-deadline/)).
- **A long session keeps working** through the upgrade and later policy changes ([Session taint](/docs/session-taint/#across-a-policy-change)).
- **New, all optional:** `openmoat gate setup` ([A code before anything is loosened](/docs/self-protection/loosening-gate/)), `mint:` secrets under `openmoat run` ([Minted credentials](/docs/keep-tokens-safe/minted-credentials/), preview), `openmoat team join` and `openmoat inventory` ([Team mode](/docs/team-rules/team-mode/)).

**To [0.26.0](/docs/releases/v0-26-0/), from 0.25.0:**

- **`openmoat init` once.** Codex, Gemini CLI, Qwen Code and Crush show their hook as out of date until you do: the new entry blocks the call when `openmoat` is missing or killed. Codex then asks you to trust the changed hook in `/hooks`, once. The same `init` records the other hooks the agents load, so nothing already there is named or blocked ([Other hooks the agents run](/docs/other-hooks/)).
- **`openmoat policy upgrade`** offers `system-files`, `stops-system`, `credential-egress`, `staging-egress` and more paths in `secrets-paths`, `persistence` and `token-egress`. After it, `ls /etc` needs review. An upgrade that would move any call toward allow is applied only with `--accept-widening`; the upgrade from the 0.25.0 default only narrows ([Benchmarks](/docs/benchmarks/#what-the-measurement-changed)).
- **New reviews with no step:** a session that read private data and untrusted content needs review for any send ([Private data and a way out](/docs/lethal-trifecta/)).
- **`when:` in rules** is refused by older binaries: update every machine before you share such a rule ([Argument conditions](/docs/policy-file/argument-conditions/)).
- **`openmoat doctor`** shows the protection score of each `openmoat run` tier and the audit log's checkpoint public key; `openmoat status` lists hook-only agents `openmoat run` can confine here.
