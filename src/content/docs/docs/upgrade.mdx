<Aside type="note" title="Read this when">

A new OpenMoat release is out, or `openmoat` says "policy update available". Coming from 0.7 or earlier, when the command was `moat`? Read [Upgrading from 0.7 or earlier](#upgrading-from-07-or-earlier) first. What a release changes, and what it needs you to run: [Releases](/docs/releases/).

</Aside>

<Steps>

1. **Upgrade the binary**

   <Tabs>
   <TabItem label="Homebrew">

   ```bash
   brew update && brew upgrade openmoat
   ```

   The formula is `crocodile-labs/tap/openmoat`. An existing `moat` install moves to it with `brew upgrade`: the tap renames `moat` to `openmoat`.

   </TabItem>
   <TabItem label="Installer">

   Run the installer again (`openmoat-installer.sh`, or `openmoat-installer.ps1` on Windows), as in the [Quick start](/docs/quickstart/). Its URL always fetches the latest release.

   </TabItem>
   <TabItem label="Cargo">

   ```bash
   cargo install openmoat --locked --force
   ```

   It installs both `openmoat` and `moat`.

   </TabItem>
   </Tabs>

   Hooks keep working after an upgrade in the same place. `openmoat doctor` confirms it, and names anything left to do.

2. **Read the release's Upgrading box**

   Each page under [Releases](/docs/releases/) starts with what that release needs, such as `openmoat init` once and then `openmoat policy upgrade` (0.12.0) or nothing at all (0.10.1). Skipped releases? Read the box of each one in between.

3. **Take the new default rules, if you want them**

   Your policy is kept as it is, so a rule the new default gained is offered, not forced. `openmoat` says "policy update available: N changes" and offers to show them.

   ```bash
   openmoat policy upgrade --dry-run   # what the new default adds, as a diff; changes nothing
   openmoat policy upgrade             # shows the diff, asks, keeps a backup and re-pins
   openmoat policy upgrade --undo      # put the previous policy back
   ```

   Lines you changed are never touched. What each line of the output means: [New default rules after an upgrade](/docs/change-the-rules/#new-default-rules-after-an-upgrade).

4. **Check the installation**

   ```bash
   openmoat --version    # prints (OpenMoat) after the version number
   openmoat status       # each agent: hook + OS sandbox, hook only, or not protected
   openmoat doctor       # drift, out-of-date hooks and sandboxes, and what to run for each
   ```

   A hook written by an older release shows as ``hook entry for … is out of date (written by an older OpenMoat); run `openmoat init` ``: run `openmoat init`. Re-run `openmoat init` only when `openmoat doctor` or the release's Upgrading box asks for it; it keeps your policy.

5. **Bring the sandboxes up to date**

   ```bash
   openmoat sandbox sync
   ```

   It rewrites the agents' sandbox settings from the current policy and re-pins them. `openmoat status` shows ``differs from the policy; run `openmoat sandbox sync` `` until you do.

6. **Restart your agents**

   An agent keeps the hook and sandbox it read when its session started. Start a new session; restart OpenClaw's Gateway, pi, OpenCode (OpenCode 2: `opencode service restart`) and Hermes Agent with its gateway. OpenClaw, pi and OpenCode report that they loaded OpenMoat's plugin only from a start after the upgrade: `openmoat status` says "plugin not loaded yet" until then. After `openmoat init` rewrote Codex's hook entry, trust it again in Codex's `/hooks`.

</Steps>

## Keep one OpenMoat installed

An older binary left elsewhere (a Homebrew install beside a `cargo install`) can still be the one a hook runs, and an older binary denies every call over a lock a newer release wrote. `openmoat doctor` names it: `hook runs …, which does not exist`, `hook runs …, a different OpenMoat binary than this one`, or `lock expects …, running …`. Remove one install, run `openmoat init` with the one you keep (by its full path, if needed), run `openmoat proxy install` again if the proxy runs as a service, and restart the agents.

On macOS 12 and earlier, Homebrew may stop and ask for a newer Xcode: upgrade with the installer or `cargo install` instead, then `brew uninstall openmoat` and run `openmoat init` once.

## Upgrading from 0.7 or earlier

From 0.8.0 the command is `openmoat`. Every install still puts a `moat` beside it that runs `openmoat`, for a few releases; then the `moat` name will be removed.

1. Run `brew update && brew upgrade` (or your install method above). The tap renames `moat` to `openmoat`.
2. Run `openmoat init` once, in your own terminal. It backs up each agent's settings file, rewrites OpenMoat's hooks to run `openmoat` instead of `moat`, and re-pins. Your policy is kept.

Until you do, the old hooks keep working through `moat`. `openmoat doctor` says when a hook still uses the old name. OpenMoat's state stays where it was: `~/.moat`, a project's `.moat/policy.yaml` and the `MOAT_*` variables are unchanged, and messages still start with `moat:`.

## What each release needs

| Upgrading to | Run |
|---|---|
| [0.12.0](/docs/releases/v0-12-0/) | `openmoat init` once (Claude Code's `SessionStart` hook for `openmoat proxy`), then `openmoat policy upgrade` (`encoded-egress`, `destructive-recoverable`, `openmoat-readonly`, the proxy key and CA under `kernel-self`, new `env-poison` names) and restart the agents; keep one OpenMoat installed (audit log schema 7) |
| [0.11.0](/docs/releases/v0-11-0/) | `openmoat policy upgrade`, then `openmoat init` and restart the agents; keep one OpenMoat installed (audit log schema 5) |
| [0.10.1](/docs/releases/v0-10-1/) | Nothing |
| [0.10.0](/docs/releases/v0-10-0/) | Nothing for a default install; `openmoat init` if OpenClaw's configuration is at another path (`OPENCLAW_CONFIG_PATH`) |
| [0.9.0](/docs/releases/v0-9-0/) | `openmoat init` once and restart the agents; `openmoat policy upgrade` and `openmoat sandbox sync`; sign repository policies and packs again |
| [0.8.0](/docs/releases/v0-8-0/) | `openmoat init` once (the new command name); `openmoat policy upgrade` |
| [0.7.0](/docs/releases/v0-7-0/) | `moat policy upgrade` |
| [0.6.0](/docs/releases/v0-6-0/) | The same release for every `moat` on the machine (audit log schema 4) |
| [0.5.7](/docs/releases/v0-5/) | `moat init` once; `moat policy upgrade` |

The notes for 0.7.0 and earlier use `moat`, the command's name in those releases; with 0.8.0 or later installed, run the same commands as `openmoat`. Every release with its downloads: [GitHub releases](https://github.com/crocodile-labs/openmoat/releases).
