<Aside type="note" title="Read this when">

Your project uses .env files, or secrets live in environment variables.

</Aside>

## What is denied

| The agent tries | Answer |
|---|---|
| `cat .env`, `source .env`, `cat .env.test`, `cat config/.env.local` | deny: `secrets-paths` (any `.env` or `.env.*`, at any depth) |
| `cat .envrc` | deny |
| `cat .env.example`, `.env.sample`, `.env.template` | allow: committed templates carry no values |
| `echo $OPENAI_API_KEY`, `$GITHUB_TOKEN`, `$AWS_SECRET_ACCESS_KEY` | deny: `env-secrets` |
| `printenv`, `env`, `export -p`, `cat /proc/self/environ` | deny: `env-dump` |
| `python -c "import os; print(os.environ['GITHUB_TOKEN'])"`, `node -e "console.log(process.env.GITHUB_TOKEN)"` | deny: `env-secrets`, a read of that variable |
| `python -c "import os; print(os.environ)"` | deny: `env-dump`, the whole environment |
| `echo $SENTRY_URL` | **defer**: the name does not look like a secret |

Variable names that are denied: anything ending in `_KEY`, `_TOKEN`, `_SECRET`, `_PASSWORD`, `_PASS`, `_PASSWD`, `_PWD`, `_CREDENTIALS` or `_DSN`, anything starting with `AWS_`, the connection strings `DATABASE_URL`, `*_DATABASE_URL`, `REDIS_URL`, `MONGODB_URI` and `MONGO_URL`, and `GITHUB_TOKEN`, `NPM_TOKEN`, `PGPASSWORD`. Other `*_URL` variables are not.

Inline code run with `python -c`, `node -e`, `ruby -e`, `perl -e`, `php -r` and similar is read too: a variable it reads by name is checked like `echo $NAME`, and code that prints the whole environment, or reads a variable whose name is chosen at run time, is denied by `env-dump`.

## Protect a variable with another name

Some variables hold a password although their names do not say so, such as `SENTRY_URL` or `AMQP_URL`. Deny them yourself with `openmoat edit`:

```yaml
deny:
  - id: my-secret-vars
    reason: these hold credentials
    env.read: ["SENTRY_URL", "AMQP_URL"]
```

## What this means for your tests

<Aside type="caution" title="Programs the agent starts cannot read .env either">

The agent's OS sandbox is built from the same policy, so `npm test` or `pytest` started by the agent cannot open `.env` or `.env.test`. A test setup that loads them gets no values, or fails.

</Aside>

Ways to handle it:

- Keep values tests need that are not secret in a file that is not named `.env*`, such as `config/test.json`.
- Run tests that need real secrets yourself, outside the agent.
- Give the agent a token through the broker instead: [Keep a token from the agent](/docs/keep-tokens-safe/).

## Variables you export

A variable set in the shell you start the agent from is still passed to the programs it runs. The agent cannot print a denied name, but a program it runs (a CLI, a test) can use the value and send it to an allowed host. Do not export production secrets in the shell you run an agent from, or broker them.
