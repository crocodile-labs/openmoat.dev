<Aside type="note" title="Read this when">

An MCP server's tools are denied with `mcp-server-changed`, you added a server, or you want its tool descriptions pinned.

</Aside>

An MCP server runs outside every sandbox, with your permissions, whatever its definition says. A postinstall script, a `git pull` or a cloned repository can change a definition or add one, and a server you accepted can later change what a tool's description tells the model. OpenMoat checks every MCP tool call against your policy, and also holds back servers and tools that nobody has reviewed.

## Server definitions are pinned

`openmoat init` pins each MCP server definition the agents read:

| Agent | Your file | The project's file |
|---|---|---|
| Claude Code | `~/.claude.json` | `.mcp.json` |
| Codex | `config.toml` | `.codex/config.toml` |
| Cursor | `mcp.json` | `.cursor/mcp.json` |

When a definition changes, or a server is added since (a cloned repository's `.mcp.json` included), the tool calls of that server are denied with rule `mcp-server-changed`. The reason names what changed. Other servers and tools keep working, and `openmoat doctor` and `openmoat status` report it.

<Steps>

1. **Review the change, in your own terminal**

   ```bash
   openmoat mcp accept <server>
   ```

   It shows the change key by key, never the value of an `env` or header entry, and asks `[y/N]`.

2. **Ask the agent to try again**

   The server's tools work again once you accept.

</Steps>

A removed server holds nothing back. A settings file that no longer parses holds back every MCP call of that agent, since it hides which servers it starts.

<Aside type="caution" title="A changed server still starts">

The agent starts its MCP servers when a session begins, before any tool call. OpenMoat refuses the server's tool calls, but it cannot stop the program from starting. To contain what a server does at start, run it with `--sandbox` (below) or run the whole agent with `openmoat run`.

</Aside>

The agent's own writes to these files ask first (`runs-later`), since the agent starts what they name in its next session.

## Pin tool descriptions too

Pinning a definition does not see a server that changes a tool's description later. For that, run a stdio server through `openmoat mcp proxy`. It is opt-in per server:

```bash
openmoat mcp wrap <server>      # one server
openmoat init --mcp-proxy       # every server, at setup
```

`openmoat mcp proxy` sits between the agent and the server and:

- leaves every tool of a server it has not pinned yet out of the tool list, and refuses its calls, naming `openmoat mcp accept <server>`, which shows each tool's name, description and input schema and asks;
- leaves a changed or new tool out of the tool list, and answers a call to it with an error naming `openmoat mcp accept <server>`; the call never reaches the server;
- records every tool call in the audit log.

`openmoat mcp accept <server>` then shows a diff of the description and schema. `openmoat mcp wrap` changes only the server's command in your own file (`~/.claude.json`, Cursor's `mcp.json`, Codex's `config.toml`), keeps a backup, and never rewrites a project's file. A server with a change you have not accepted is skipped.

### Run the server in a sandbox

```bash
openmoat mcp wrap <server> --sandbox
```

The server then runs under `openmoat run`: the sandbox made from your policy, with network only to the hosts the policy allows. Many servers need writes (package caches) or hosts the default policy does not list, so this is a choice per server. `--sandbox` cannot be used for an agent that itself runs under `openmoat run`.

### Undo it

```bash
openmoat mcp unwrap <server>
```

`openmoat uninstall` also puts every wrapped server back as it was.

## Only you accept

`openmoat mcp accept`, `openmoat mcp wrap` and `openmoat mcp unwrap` are denied to agents (`kernel-self`), terminal wrappers included, and refuse to run when an agent started them.

## Good to know

- **First sight is not trusted.** `openmoat mcp proxy` holds back a new server's tools until you accept them. To pin what a server lists the first time instead, set `mcp: { trust_first_sight: true }` in the policy; `openmoat policy lint` warns about it.
- **Not pinned:** prompts, resources, output schemas, annotations and tool results.
- **Not covered by the proxy:** remote (HTTP) servers, Claude Code plugin servers and managed MCP settings.
- **One name, every project.** A changed server in one project of `~/.claude.json` also holds back a server with the same name in another project, until you accept it.

<Aside type="note" title="Upgrading from 0.5.6 or earlier">

A lock from before 0.5.7 has no MCP pins, so nothing is held back until `openmoat init` or `openmoat mcp accept` pins the servers. `openmoat doctor` says so.

</Aside>
